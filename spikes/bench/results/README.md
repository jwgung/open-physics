## 1차 대비

- Godot은 측정 방식을 웹과 맞춘 뒤에도 S1 27.1→26.0, S2 11.6→11.6, S3 24.3→24.3fps로 거의 같았다. delta smoothing과 로딩 프레임은 1차 결과를 왜곡하지 않았다.
- web S1은 15.3→20.0fps로 달라졌다. 코드는 S1에 영향이 없었으므로 회차 간 편차(WebGPU 경로의 셰이더 캐시 등)로 본다.

## 웹 S2 메모리 증가

10분 지속 측정에서 web-threejs의 PSS가 시작 189 MB에서 종료 1,137 MB로 거의 선형으로 늘었다(약 90 MB/분). 1차 측정에서도 같은 양상이었다. 같은 조건에서 Godot은 238 MB에서 225 MB로 평탄했다. S2는 20초마다 물체 10개를 다시 떨어뜨리지만 새 메시·물리 바디를 만들지 않는다(`drop`은 위치·속도만 바꾼다). 런타임에 새로 생기는 것은 드래그·레이캐스트 경로의 JS 임시 객체뿐이고, 측정 중에는 입력이 없었다. 따라서 원인은 렌더러(WebGPU) 또는 Rapier wasm 쪽 누수로 의심되며 아직 밝히지 못했다.

## WebGPU 누수와 WebGL 대안

웹 S2 메모리 증가의 원인은 [누수 조사](../leak-repro/README.md)에서 확인했다. Android WebView 155의 WebGPU(compatibility 모드)가 이 기기에서 프레임마다 네이티브 힙을 누수한다. three.js·Rapier가 없는 최소 페이지에서도 재현된다.

누수를 피하려고 측정한 `web-classic`(WebGLRenderer)은 결과가 엇갈렸다. 메모리는 10분 동안 110→117 MB로 평탄했다. 그러나 S1 5.8, S2 7.9 fps로 Godot(26.0, 11.6)보다 느렸다. 미리 정한 판정 기준은 "S2가 Godot 이상이고 10분 메모리가 평탄할 것"이었고, 이를 넘지 못했다. 10분 저하의 -27.2%는 지속 측정 중 FPS가 오히려 오른 것으로, 이 경로의 프레임 시간이 크게 흔들린다는 뜻이다.

## 비교 시 주의: 렌더 설정이 같지 않다

| 항목 | web-threejs | godot |
|---|---|---|
| 안티에일리어싱 | `antialias: true`(MSAA 기본 4x 계열) | `msaa_3d=1`(2x) |
| 렌더 해상도 | `setPixelRatio(devicePixelRatio)` 네이티브 | 기준 720×1280 + `canvas_items` 스트레치, 3D 실제 해상도는 미확인 |
| S2 그림자 | PCF, 2048 맵 1장 | 방향광 `PARALLEL_2_SPLITS` |

S2의 FPS 역전(godot 11.6 / web 25.8)은 그림자 패스 차이 때문일 수 있다. 그렇다면 엔진 우열을 보여주는 결과가 아니다. S1에서는 web이 AA·해상도 면에서 더 무겁다. 같은 설정으로 다시 측정하는 것은 Phase 1 품질 단계 작업에 포함한다.
