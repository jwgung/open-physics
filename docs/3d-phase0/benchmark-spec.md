# 3D 스택 비교 측정 기준 (Phase 0 · T1)

> **Status:** Phase 0 측정 기준
> **Purpose:** 두 후보 스택(웹 스택 + Capacitor, Godot 4 + Jolt)을 같은 장면·같은 기기·같은 절차로 측정해 비교할 수 있게 한다.

후보 조사는 [3D 스택 후보 조사](../research/3d-stack-candidates.md), 결정은 이후 ADR에 남긴다.

## 1. 합격 기준

| 항목 | 커트라인 | 비고 |
|---|---|---|
| 평균 FPS | S1·S2·S3 모두 ≥ 58 | 60Hz 화면 기준 |
| 1% low FPS | ≥ 50 | 순간 끊김 판단 |
| frame time p95 | ≤ 18 ms | |
| 10분 지속 | 마지막 1분 평균 FPS가 첫 1분 대비 저하 ≤ 5% | 스로틀링 판단 |
| S3 공식 일치 | 아래 4절 오차 기준 통과 | 미달 시 물리 구조 재합의 |

커트라인 미달 후보는 탈락한다. 둘 다 통과하면 사용자가 두 APK를 직접 만져 그래픽·손맛으로 고르고, 동률이면 개발 효율·웹 품질로 정한다.

참고 지표(탈락 기준 아님): 콜드 스타트(앱 아이콘 → 첫 프레임), APK 크기, 최대 메모리(PSS), 배터리 온도 상승, 웹 빌드 전송 크기·첫 프레임 시간·PC 브라우저 FPS.

## 2. 측정 기기와 환경

- 기기: **Galaxy Tab A with S Pen 8.0 (SM-P200)**. 2019년 보급형으로 Exynos 7904, RAM 3GB, Android 11, WebView 155, 60Hz다. 기준 기기(중급폰)보다 성능이 낮은 **하한 기기**로 쓴다.
  - 두 후보의 상대 비교는 이 기기 결과로 한다.
  - 1절 커트라인은 이 기기에서 "최고 품질 30fps 이상, 그래픽 품질 단계를 낮추면 60fps"로 해석한다. 중급폰 60fps 확인은 중급 기기를 확보한 뒤 한다.
- 측정 시작 시 모델·Android 버전·Android System WebView 버전·화면 주사율을 결과표 머리에 기록한다.
- 120Hz 기기는 60Hz로 고정하고 측정한다.
- 조건: 무선 디버깅(`adb pair`·`adb connect`, Android 11+)으로 연결하고 케이블을 분리해 충전 발열을 뺀다. 배터리 ≥ 80%, 밝기 50%, 비행기 모드, 다른 앱 종료, 실온, 측정 사이 5분 냉각.
- 빌드: 두 후보 모두 release 빌드, 해상도 배율은 기기 기본값(devicePixelRatio·Godot `window/stretch` 기본).
- 웹 스택은 WebGL2를 품질 기준선으로 측정하고, 기기에서 `navigator.gpu`가 잡히면 WebGPU 경로도 따로 측정해 백엔드를 결과표에 표시한다.
- iOS는 이번 단계에서 측정하지 않는다. 웹 스택이 이기면 ADR 확정 전에 별도로 확인한다.

## 3. 기준 장면

세 장면 모두 같은 화면 비율(세로 모드), 같은 카메라 시작 위치, 같은 물체 수·크기를 쓴다. 장면 전환 버튼과 FPS 오버레이 토글을 둔다.

### S1 궤도 (그래픽 상한)

- 중심 천체 1개(발광 재질 + 블룸) + 행성 8개(PBR, 텍스처 2048², 노멀맵), 고리 행성 1개.
- 궤도선 8개, 별 배경(큐브맵 또는 파티클 5,000개).
- 운동: 원궤도 해석해(`circularOrbitSpeed`, `/home/capalace/Git/open-physics/src/physics/laws/orbit.ts`)로 위치 갱신. 이 장면은 렌더링 부하 측정용이다.
- 카메라: 30초마다 전체 보기 → 행성 따라가기를 자동 반복(측정 재현성).

### S2 역학 빈 실험실 (물리·렌더링 혼합 부하)

- 바닥 1개, 30° 빗면 1개, 고정 블록 3개.
- 움직이는 물체 50개(상자 25, 공 25), 재질 3종(고무·나무·금속 — 기존 `MATERIALS` 반발·마찰값 재사용, `/home/capalace/Git/open-physics/src/app/physics-playground.ts`).
- 방향광 실시간 그림자 1개 + 환경광, 물체 PBR.
- 시작 시 높이 3~6 m에서 무작위 낙하(고정 seed) → 쌓임·굴러감.
- 조작 확인: 물체를 조작 평면(바닥·면 위)에서 드래그·스냅, 두 손가락 카메라 회전·확대. 측정 실행 중에는 자동 입력 없이 20초마다 물체 10개를 재낙하시켜 부하를 유지한다.

### S3 안내형 빗면 마찰 (공식 보정 검증)

- 각도를 바꿀 수 있는 빗면 1개, 상자 1개(1 kg), g = 9.81 m/s².
- 마찰계수: 정지 μs = 0.5, 운동 μk = 0.4(이 장면 전용 고정값).
- 화면 표시: 빗면 각도, 중력 접선 성분, 최대 정지 마찰력, 가속도, 이동 거리.
- 보정 방식은 각 스파이크가 정하되, 아래 기준값을 만족해야 한다.

## 4. S3 공식 기준값과 오차 기준

기준값은 기존 TS 공식 코어와 같은 식으로 계산한다.

| 검사 | 공식 | 기준값 | 허용 오차 |
|---|---|---|---|
| 정지 마찰 임계각 | θc = atan(μs) | 26.565° | 시작 각도 26.0°에서 정지 유지, 27.0°에서 1초 안에 미끄러짐 시작 |
| 미끄럼 가속도(θ=35°) | a = g(sinθ − μk·cosθ) | 2.412 m/s² | 표시값 완전 일치(공식 계산값 표시), 측정 가속도 ±1% |
| 이동 거리(θ=35°, 정지 출발) | s = ½at² | t=1s: 1.206 m, t=2s: 4.825 m | ±1% |
| 정지 상태 안정성 | — | θ=20°에서 10초 동안 이동 0 | 누적 이동 ≤ 1 mm |

이동 거리·가속도는 엔진 내부 시간(고정 timestep) 기준으로 기록해 렌더링 FPS와 무관하게 판정한다. 각 스파이크는 이 표를 자동 테스트(헤드리스 실행)로 재현해야 한다.

## 5. 측정 절차

1. 앱 설치 후 1회 실행·종료(셰이더 캐시 생성).
2. 각 장면: 30초 워밍업 → 60초 측정 × 3회. 회차 사이 앱 재시작.
3. 지속 측정: S2를 10분 연속 실행.
4. 콜드 스타트: `adb shell am force-stop` 후 실행 × 5회 중앙값.

## 6. 기록 형식

앱은 1초마다 logcat 태그 `OPBENCH`로 JSON 한 줄을 남긴다.

```json
{"t":12,"scene":"S2","fps":59.8,"p50ms":16.6,"p95ms":17.4,"p99ms":21.0,"frames":60,"long":0}
```

- `t`: 측정 시작 후 초, `long`: 33 ms를 넘은 프레임 수.
- 프레임 시간은 웹은 `requestAnimationFrame` 간격, Godot은 `_process` delta로 잰다.

호스트 수집기 `/home/capalace/Git/open-physics/spikes/bench/collect.sh`가 `OPBENCH` 로그와 10초마다 배터리 온도·thermal status·메모리를 함께 저장한다. 결과는 `spikes/bench/results/<후보>-<장면>-<회차>.jsonl`로 남기고, 결과표는 `spikes/bench/results/README.md`에 정리한다.
