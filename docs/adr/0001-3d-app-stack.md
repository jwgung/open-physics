# ADR 0001: 3D 앱 스택 — Three.js + Rapier + Capacitor

> **Status:** 제안됨 (iOS 확인 전까지 조건부)
> **Date:** 2026-10-21
> **Context docs:** [측정 기준](../3d-phase0/benchmark-spec.md) · [후보 조사](../research/3d-stack-candidates.md) · [1차 실측 결과](../../spikes/bench/results/README.md)

## 맥락

Open Physics를 3D 모바일 앱으로 출시한다. 대상은 iOS와 Android이고, 무료·무광고이며 아동도 사용한다. 웹 버전도 같은 콘텐츠로 유지하되, 그래픽은 앱보다 한 단계 낮아도 된다. 첫 출시는 역학 3D다. 하나의 범용 3D 물리 엔진 위에서 안내형 실험의 핵심 운동과 표시 수치를 교과서 공식값으로 보정한다. 개발은 AI 에이전트가 CLI로 주도한다.

후보는 두 가지였다. 같은 기준 장면 S1~S3로 스파이크를 만들어 비교했다.

- A: Three.js r186(WebGPURenderer, WebGL2 fallback) + Rapier 0.21 + Capacitor 8
- B: Godot 4.7.2 + Jolt

## 측정 결과 요약

하한 기기 SM-P200(Mali-G71)에서 측정했고, 두 스파이크 모두 최적화하지 않은 상태다. 아래 수치는 셀프 리뷰에서 측정 방식 차이를 바로잡은 뒤의 2차 측정값이다. 1차 측정과 큰 차이는 없었다([결과](../../spikes/bench/results/README.md)). 측정 조건은 측정 기준 2절과 다르다. USB로 연결해 충전 중이었고, 밝기는 128/255, 웹은 backend auto(WebGPU)로만 측정했다. 콜드 스타트는 첫 프레임이 아니라 `am start -W` TotalTime이다. 충전 중 측정은 발열에 불리한 조건인데도 10분 동안 thermal status 0, 온도 변화 ±0.1°C였다. 그러므로 "스로틀링 없음"은 이 기기의 낮은 GPU 부하 상태에서의 결과로 읽는다. 두 스파이크의 안티에일리어싱, 렌더 해상도, S2 그림자 설정이 서로 달라서 장면별 FPS 차이를 엔진 우열로 읽지 않는다([결과 주의 사항](../../spikes/bench/results/README.md#비교-시-주의-렌더-설정이-같지-않다)).

| 항목 | Godot + Jolt | Three.js + Rapier |
|---|---|---|
| S1 궤도 FPS | **26.0** | 20.0 (WebGPU) |
| S2 빈 실험실 FPS | 11.6 | **25.8** |
| S3 빗면 마찰 FPS | 24.3 | 22.1 |
| 10분 스로틀링 | 없음 | 없음 |
| 최대 메모리(PSS), 90초 측정 | **322 MB** | 484 MB |
| S2 10분 PSS 추이 | **238 → 225 MB (평탄)** | 189 → 1,137 MB (약 90 MB/분 증가) |
| APK | 93.7 MB | **5.1 MB** |
| 웹 빌드(gzip) | 36.8 MB | **1.9 MB** |
| S3 공식 일치 | 통과(오차 ≤ 0.02%) | 통과(오차 ≤ 0.44%) |
| 공식 코어 | GDScript로 이식 후 parity 테스트 | 기존 TS 코어 직접 import |

## 판정

1. **커트라인**: 두 후보 모두 하한 기기에서 최고 품질 30fps에 미달했다. 품질을 낮춘 단계는 측정하지 않았다. Plan의 재합의 경계("둘 다 미달")에 해당해 사용자에게 2차 측정, 즉시 체감 평가, 중급 기기 재측정 중 하나를 물었다. 사용자는 재합의 없이 현재 결과로 진행하기로 했다(2026-10-21). 장면별 우열이 엇갈려 성능으로는 가르지 않는다. 저품질 60fps 기준은 Phase 1 출시 기준으로 넘긴다.
2. **체감 평가**: 사용자가 생략하고 현재 결과로 진행하기로 했다(2026-10-21).
3. **동률 규칙(개발 효율·웹 품질)**: A가 앞선다.
   - 기존 TS 공식 코어와 루트 테스트 440개(`npm test`, 2026-10-21 기준)를 그대로 쓴다. B는 공식마다 생성기·JSON·GDScript·Godot 테스트 네 곳을 고쳐야 한다.
   - 웹 버전이 앱과 같은 코드·같은 렌더러로 나온다. B의 웹은 Compatibility 렌더러에 36.8 MB다.
   - CI가 Node 하나로 끝난다. 앱 크기도 18배 작다.

**결정: A(Three.js + Rapier + Capacitor)를 채택한다.**

## 아동 정책

무료·무광고·아동 포함 결정에 따라 계정·서버·광고·제3자 추적을 두지 않는다. 후보 조사 5절에 따르면 Apple Kids Category와 Google Play Families 요건은 광고·분석 SDK를 넣지 않는 한 두 스택 모두 충족할 수 있어 스택 선택을 가르지 않는다. 외부 링크는 보호자 확인(parental gate) 뒤에 두고, 개인정보처리방침(수집 없음)을 둔다. Capacitor 기본 `INTERNET` 권한은 Phase 1에서 필요성을 따져 제거하고, 네트워크 요청이 없는지 점검한다. 스파이크에 남은 디버그 훅 `window.__opspike`도 제거한다.

## 조건과 후속 확인

- **iOS 확인(필수)**: Plan 결정에 따라 웹 스택이 이겼으므로, 이 ADR을 확정하기 전에 iOS를 확인한다. 중급 iPhone 대여, macOS CI 빌드, Apple 개발자 계정이 필요하다. 확인할 항목은 WKWebView에서의 S1~S3 FPS, 메모리 한도로 앱이 종료되는지, WebGPU 사용 가능 여부다. 실패하면 B를 재검토한다.
- **메모리**: 웹 S2는 10분 동안 PSS가 거의 선형으로 늘어 1.1 GB에 이르렀다. 3 GB 기기에서 위험한 수준이다. 장면은 새 객체를 만들지 않으므로 렌더러(WebGPU) 또는 Rapier wasm 쪽 누수로 의심된다. Phase 1 첫 Task에서 원인을 찾아 없애고, 10분 지속 측정에서 PSS가 평탄하게 600 MB 이하로 유지되는지 확인한다. 해결하지 못하면 이 ADR을 다시 검토한다.
- **그래픽 단계**: 저·중·고 품질 단계(해상도 배율, 그림자, 블룸, 텍스처 크기)를 Phase 1 셸의 기본 기능으로 둔다. 하한 기기 저품질 60fps와 중급폰 고품질 60fps를 출시 기준으로 다시 측정한다.
- **렌더러 경로**: 하한 기기에서는 WebGPU가 잡혔지만 S1이 느렸다. WebGL2 경로와 비교 측정해 기본 백엔드를 정한다.
- **텍스처**: 런타임 생성을 KTX2 압축 텍스처로 바꿔 첫 프레임 지연(약 10초)과 GPU 메모리(약 230 MB)를 줄인다.
- **공식 보정 일반화**: S3 방식(엔진 마찰 0 + 공식 마찰력 주입)은 알려진 단일 접촉에서만 검증됐다. 빈 실험실의 일반 접촉에서는 Rapier contact modification 범위를 조사해 별도로 설계한다.
- **결정론**: `rapier3d-deterministic`는 아직 시험하지 않았다. 기기 간 재현이 필요한 실험이 생길 때 확인한다.

## 결과

- 3D 앱은 같은 저장소 `apps/` 아래 TS 패키지로 시작한다. 물리 공식 코어 `src/physics/laws/`는 보정 기준으로 공유한다.
- 웹 2D는 유지보수만 한다(기능 추가 동결).
- `spikes/godot/`는 비교 근거로 남기고 더 개발하지 않는다.

## Phase 1 Task 초안 (발행 전 사용자 승인 필요)

1. 3D 앱 셸: Capacitor 프로젝트, 카메라 모드, 터치 제스처, 조작 평면·스냅, 품질 단계, 2D 패널 레이아웃
2. 메모리·렌더러 경로 조사와 KTX2 텍스처 파이프라인
3. 엔진 위 공식 보정 계층 일반화와 공식 테스트 연결
4. 역학 안내형 10개 3D 이식(실험별로 나눠 발행)
5. 역학 빈 실험실 3D(고정 블록·줄·용수철·지렛대·도르래·힘·중력원·물)
6. 출시 준비: 서명, 스토어 자료, 개인정보처리방침(수집 없음), Kids/Families 정책, 모바일 CI, iOS 실기기 확인
