# low 단계 3D 선명도 — 540 px → 900 px + MSAA 2x

- 기기: SM-P200 (Galaxy Tab A 8.0 2019, Exynos 7904 / Mali-G71 MP2, Android 11, 1200×1920, 60 Hz) — 하한 기기
- 일시: 2026-10-24 08:21–09:36
- 계기: 사용자가 태블릿에서 "머야 왜케 깨져". low가 3D를 짧은 변 540 px(`view_scale` 0.45, MSAA 없음)로 그려 화면에 늘리니 구름·나무·고양이 가장자리가 계단처럼 보였다(`../phase1-task4g2/screens/toon-front.png`와 같은 화면).
- 빌드
  - 후보 측정: `feat/dugi-rabbit` 9c03381 release APK + 측정용 덮어쓰기 `--q-view_scale=<값>,--q-msaa=<0|2>`(코드는 그대로).
  - 최종: 같은 브랜치 + 이 작업(low `view_scale` 0.75·`msaa` 2, 외곽선 최소 두께 1.5 px).
- 조건
  - USB 연결(adb, SM-P200만 사용), 충전 중. 기기 설정(밝기, `stay_on_while_plugged_in`, 화면 꺼짐, `wm size` 1200x1920)은 바꾸지 않았다.
  - fps 측정 중에는 호스트 Godot를 돌리지 않았다(APK 빌드는 측정 사이에만).
  - 끝난 뒤 앱의 품질 단계는 low(`user://quality.txt`).

## 1. 확인한 것

- 확대 필터: 3D 화면은 `TextureRect`의 `TEXTURE_FILTER_LINEAR`(쌍선형)로 늘린다(`scripts/shell/view_3d.gd`). 계단의 원인은 필터가 아니라 540 px 버퍼와 MSAA 없음이다. 그대로 둔다.
- UI: 원본 해상도(루트 `canvas_items` 스트레치, `ui_mode=native`). 바꾸지 않는다.
- 목록 화면: 3D가 없다(`IslandBanner`는 2D 다각형). 측정에서 뺐다.
- 장면 고르기: 던지기는 그리는 양이 가장 많다(고양이·울타리·나무, 최종 빌드 프리미티브 약 14,000·드로우콜 45, 자유 낙하 6,100·36, 궤도 8,300·33). 자유 낙하는 움직이는 공이 셋으로 물리 몸체가 가장 많다(충돌 2개, 나머지 1개). 궤도는 Task 4d부터 33 ms 넘는 프레임이 가장 많던 실험이라 더했다. 충돌·용수철·진자·부력 등 나머지는 0.75에서 재지 않았다.

## 2. 후보 측정

명령: `OPBENCH_EXPERIMENT=<id> OPBENCH_CTL=<덮어쓰기> OPBENCH_SUSTAINED=0 OPBENCH_OVERWRITE=1 OPBENCH_RESULTS_DIR=<dir> apps/lab3d/tools/bench_device.sh low 1 90 30`

- 화면: 가로, 사이드바 닫힘, 정면 시점, 기본 조건. 조작 `--auto-drag=4`(4초마다 끌어 놓고 0.4초 뒤 놓기. 던지기는 고양이가 던짐). "놓기만"은 `OPBENCH_PLAY=--auto-release=4`.
- 셰이더 캐시 1회 → 30초 예열 → 90초 × 1회. 판정 기준은 Task 4 이후와 같은 90초 1회 평균 ≥ 59.5 fps.
- 평균 = 프레임 수 / 시간, 최저 = 초당 fps 최저, 33 ms 넘는 프레임 = OPBENCH `long` 합, 1% low = 초당 p99 프레임 시간 평균의 역수(`summarize.mjs`와 같음), GPU = `gpu-clock-low.log` Mali 클럭 평균(Compatibility는 GPU 시간 측정이 없어 여유를 클럭으로 본다. 최대 845 MHz).

- 0.85는 던지기가 통과하지만 GPU 712 MHz로 남은 여유가 약 16 %라 열로 클럭이 묶이면(Task 1: 845 → 450 MHz) 버티기 어렵다고 보고 뺐다.
- 궤도(끌기 재생)는 기존 0.45에서도 59.50으로 경계이고, 놓기만 하면 0.45·0.75 모두 59.8 수준이다. 33 ms 넘는 프레임이 끌어 놓는 4초 주기에 몰리고 그 초에 118 ms 프레임이 있다. 끄는 동안 공식 미리보기(`PhysicsLaws.orbit_analyze`, 최대 1200 스텝)와 경로 점 갱신이 CPU에서 도는 것으로 추정한다(미검증). 스파이크는 해상도와 상관없이 기존 0.45에도 있었지만, 해상도를 올리면 GPU 여유가 줄어 33 ms 넘는 프레임이 늘어난다(0.45 35개 → 0.6 26개 → 0.75 47개 → 0.85 72개, 한 번씩이라 잡음이 크다).

### 외곽선 두께

캐릭터 외곽선 최소 두께를 "화면 높이의 0.35 %"에서 "3D 렌더 버퍼 1.5 px"로 바꿨다(`ArtKit.OUTLINE_PIXELS`, `art_outline.gdshader`). 0.35 %는 540 px·MSAA 없음에서 끊기지 않는 가장 얇은 값(약 1.9 px)으로 고른 것이라, 900 px에서는 3.2 px로 필요 이상 두껍다. 끊기는지는 렌더 픽셀 수와 MSAA로 정해지므로 픽셀 수로 둔다. 기본 정면 시점(던지기 대기)에서 비교했다.

- 1.0 px: 귀 끝·봉투 윗단에서 선이 흐려지고 군데군데 끊김.
- 1.5 px(채택): 끊김 없음.
- 가까이 보면 그대로 세계 두께 0.010 m가 이긴다(바뀌지 않음).

## 5. 남은 일·판단 필요

- 궤도 실험을 끌기 재생으로 재면 58.84 fps로 기준 미달이다. 같은 측정이 기존 low에서도 59.50으로 경계였고(4d 기록 59.7, 1% low 33.7), 놓기만은 59.66으로 통과한다. 궤도 끌기 중 CPU 스파이크를 줄이는 일은 이 작업 범위 밖이라 남긴다.
- 10분 지속에서 GPU는 끝 무렵 845 MHz까지 오르기도 했지만 fps 저하는 0.1 %다. 더 더운 환경·더 긴 사용은 재지 않았다.
- medium(720 px)·high(1200 px)도 외곽선이 1.5 px 규칙을 쓴다. 두 단계는 Mobile 렌더러라 이번에 SM-P200에서 다시 재거나 찍지 않았다.
