# Phase 1 Task 1 결과 — S2 병목과 품질 단계

- 기기: SM-P200 (Galaxy Tab A 8.0 2019, Exynos 7904 / Mali-G71 MP2, Vulkan 1.1, Android 11, 1200×1920, 60 Hz) — 하한 기기
- 일시: 2026-10-21. 병목 조사 15:00–16:30, 단계별 측정 1차 16:35–18:10, 2차 18:11–19:45(표는 2차)
- 빌드: Godot 4.7.2 + Jolt, release APK. 단계 측정은 커밋 `b207857`의 스파이크
- 계약: [Phase 1 README의 Task 1 상세](../../../../docs/3d-phase1/README.md#task-1-상세)

## 요약

- **판정: 저품질에서 S1~S3 모두 SM-P200 60 fps에 닿았다.** 2차 측정 평균 59.8 fps(S1·S2·S3), S2 10분 지속 59.6–59.8 fps로 저하 없음, PSS 149 → 152 MB로 평탄. Task 2로 넘어갈 수 있다.
- 병목은 GPU다(CPU·드로우콜·물리·지오메트리 아님). Mobile(Vulkan) 렌더러가 원본 출력 해상도(1200×1920)에서 내용과 무관하게 쓰는 고정 비용 약 20 ms, S2 절차적 하늘 약 27 ms, 그림자 2분할 약 18 ms가 대부분이다(GPU 450 MHz 기준).
- 이 기기는 AP 온도가 오르면 GPU를 845 → 450 MHz로 묶는다. Phase 0의 S2 11.6 fps는 이 제한 상태 값이고, 식은 상태에서는 같은 빌드가 21.6 fps다.
- 저품질은 Compatibility(OpenGL ES 3) 렌더러 + 루트 뷰포트 540 + 그림자·하늘·glow 끔이다. 같은 설정을 Mobile 렌더러로 그리면 43–47 fps에 그쳤다. 그래서 low만 렌더러가 다르고, 단계 전환 시 앱이 한 번 재시작한다.
- 남은 차이: medium은 38–42 fps, high는 Phase 0과 같은 11–28 fps다. low의 1% low(초당 최악 프레임)는 측정 수집기의 메모리 조회 때문에 약 36 fps로 나온다(7절).

## 1. 재현 루프

`spikes/bench/godot-variant.sh`가 한 변형을 2분 안에 잰다. 재빌드 없이 launch intent의 `opargs` extra로 장면·품질 단계·단일 항목을 바꾼다.

```bash
spikes/bench/godot-variant.sh s2-msaa0 20 40 --scene=S2 --quality=high --q-msaa=0
```

- 고정 조건: S2 seed 20261021, 카메라 기본값(거리 13 m, 같은 각도), 입력 없음. 앱을 `force-stop` 후 시작하고 20초(일부 15초) 기다린 뒤 40초(일부 30초) 기록한다.
- 같은 1초 창에 OPBENCH(측정 기준 6절 그대로)와 OPPERF(Godot 모니터, 필드는 [스파이크 README](../../../godot/README.md#opperf-로그-phase-1))를 남긴다.
- 2초마다 Mali GPU 클럭(`/sys/class/misc/mali0/device/clock`)과 AP 온도(`dumpsys thermalservice`)를 함께 기록한다. 이 기기에서 루트 없이 읽힌다.
- 결과 원본은 [`bisect/`](./bisect/)에 있다. `<이름>.log`가 OPBENCH+OPPERF, `<이름>.clk`가 "클럭(kHz) AP 온도(°C)"다. 표는 `node spikes/bench/variant-summary.mjs`로 만들었다.
- 조사 중에는 실험용 항목(`--q-scale` 3D 해상도 배율, `--q-multimesh`, `--q-sphere_segments`, `--dbg-physics=0` 물리 정지, `--dbg-3d=0` 3D 끔, `--dbg-hide`·`--dbg-statics=0` 물체·고정물 숨김, `--dbg-tonemap=linear`, `--dbg-env=0` WorldEnvironment 제거, `--dbg-vp=<너비>` 루트 뷰포트 너비)을 임시로 넣었다. 판정이 끝난 뒤 제거했고, 채택한 항목만 품질 단계(`render_width`, `msaa`, `shadow_splits`, `shadow_size`, `sky`, `glow`, `renderer`)로 남겼다. Compatibility 렌더러 비교(`gl-*`)는 `rendering_method.mobile`만 바꾼 빌드로 쟀다.
- `bisect/`의 OPPERF 필드 이름은 최종 형식으로 바꿔 저장했다(조사 당시 `cpu_ms`·`phys_ms`·`rcpu_ms`·`objs`·`q`). Compatibility 실행의 GPU 시간 0은 `null`로 바꿨다.

## 2. 먼저 드러난 변수: GPU 클럭 제한

같은 Phase 0 빌드의 S2가 실행마다 16.5 fps와 11.5 fps로 갈렸다. GPU 클럭을 같이 기록하자 원인이 보였다.

| 실행 | GPU 클럭 | S2 high FPS | GPU ms | GPU Mcycle/프레임 |
|---|---|---|---|---|
| 식은 상태에서 시작(`high-cool`) | 845 MHz | 21.3 | 44.0 | 37.2 |
| AP 약 42–47 °C 이후(`v-base`) | 450 MHz | 11.4 | 83.3 | 37.5 |

- AP(SoC) 온도가 오르면 GPU가 845 MHz에서 450 MHz(가끔 545 MHz)로 묶인다. 배터리 온도는 28–29 °C로 거의 변하지 않아, 측정 기준의 배터리 온도로는 이 상태가 보이지 않는다. thermal status도 0이었다.
- 프레임당 GPU 사이클은 두 상태에서 같다(약 37 M). S2는 GPU에 묶여 있고, GPU 시간은 클럭에 반비례한다.
- Phase 0의 S2 11.6 fps는 450 MHz 상태 값이다. 10분 지속 사용에서는 이 상태가 기본이므로, 60 fps 목표는 450 MHz 이하에서 GPU 약 7 M 사이클/프레임 안에 들어야 한다는 뜻이다.
- 아래 비교는 모두 450 MHz 상태에서 했다. 부하가 가벼우면 DVFS가 343 MHz로 내려가므로 표에 클럭을 같이 적고, 사이클(GPU ms × MHz)로도 비교한다.

## 3. 가설과 판정

조사 전 순위(근거: S3처럼 물체가 거의 없는 장면도 24 fps였으므로 화면 크기에 비례하는 비용을 먼저 의심했다):

1. 3D 해상도(1200×1920 원본, 픽셀 비용)
2. 방향광 그림자(2분할, 아틀라스 2048)
3. MSAA 2x
4. 하늘·환경광(절차적 하늘 배경, 하늘 반사)
5. 지오메트리(공 25개 × 64×32 분할)
6. 드로우콜(MeshInstance3D 50개)
7. Jolt 물리

### 3-3. 렌더러: Mobile(Vulkan) vs Compatibility(OpenGL ES 3)

`rendering_method.mobile`만 바꾼 빌드로 같은 변형을 쟀다(Compatibility는 GPU 타임스탬프가 없어 GPU ms가 없다).

|---|---|---|
| S2 high(원본 해상도, 그림자 2분할, 하늘, MSAA 2x) | 11.4 | 8.4 |
| S2 그림자 끔·단색 배경, 원본 해상도 | 23.6 | 19.9 |
| S2 그림자 끔·단색 배경, 루트 뷰포트 720 | 39.1 | 40.3 |
| S2 그림자 끔·단색 배경, 루트 뷰포트 540 | 44.1 | 60.0 |
| S2 같은 조건 + MSAA 끔 | 43.0 | 60.0 |
| S2 루트 뷰포트 540 + 직교 그림자 1024 | 39.9 | 42.5 |
| S2 루트 뷰포트 540 + 하늘 | 39.3 | 37.8 |
| S1 저품질 조건(540, glow 끔) | 47.4 | 60.0 |
| S3 저품질 조건(540, 그림자 끔) | 47.0 | 60.0 |

- 무거운 설정에서는 Mobile이 낫다(S1 high 26.0 vs 15.1). 가벼운 설정에서는 Compatibility만 60 fps에 닿는다. Mobile 렌더러는 이 기기에서 내용과 무관한 고정 비용 때문에 60 fps 예산(16.7 ms)을 안정적으로 지키지 못한다.

### 3-4. 판정

| 가설 | 판정 | 근거 (450 MHz) |
|---|---|---|
| 1. 3D 해상도 | 부분 확인 | 배율 0.5에서 83.3 → 41.2 ms. 그러나 배율과 무관한 고정 비용이 약 20 ms 남는다 |
| 2. 그림자 | 확인 | 끄면 −17.9 ms. 직교 1장 −2.1 ms, 아틀라스 1024 −5.2 ms |
| 3. MSAA 2x | 반증 | 끄면 오히려 +15.6 ms(두 번 재현). 가벼운 조합에서는 차이 없음 |
| 4. 하늘·환경광 | 확인(예상보다 큼) | 단색 배경으로 −27.4 ms. 단일 항목 중 가장 크다 |
| 5. 지오메트리 | 반증 | 프리미티브 96k → 7k에도 −1.9 ms |
| 6. 드로우콜 | 반증 | MultiMesh로 63 → 34콜, 렌더 CPU 2.4 → 2.0 ms, GPU는 +2 ms. CPU 렌더 제출은 병목이 아니다 |
| 7. Jolt 물리 | 프레임 병목 아님 | 물리를 멈춰도 GPU 시간이 그대로다. 3D를 끄면 60 fps. 다만 물리 스텝이 6–9 ms로 60 fps CPU 예산의 절반을 쓴다 |
| 추가: 출력 해상도 고정 비용 | 확인 | 빈 장면도 원본 해상도에서 20.9 ms, 루트 뷰포트 720에서 12.3 ms |
| 추가: 렌더러 | 확인 | 같은 저품질 조건에서 Mobile 43–47 fps, Compatibility 60 fps(S1~S3) |

## 4. 병목 결론

S2는 GPU에 묶여 있다. CPU(렌더 제출 2.4 ms, 물리 6 ms)는 병목이 아니다. GPU 비용은 세 덩어리다.

1. 출력 해상도에 붙는 고정 비용: Mobile 렌더러가 1200×1920에서 내용과 무관하게 약 17–20 ms를 쓴다(후처리·톤매핑·블릿).
2. 절차적 하늘 배경과 하늘 반사: 약 27 ms.
3. 방향광 그림자 2분할: 약 18 ms.

여기에 열 제한(845 → 450 MHz)이 겹쳐 짧은 측정과 지속 사용의 성능이 거의 두 배 차이 난다. Phase 0의 S2 11.6 fps는 제한된 상태의 값이다.

## 5. 품질 단계

정의는 [`spikes/godot/scripts/quality.gd`](../../../godot/scripts/quality.gd)에 있고 사용법은 [스파이크 README 3-1절](../../../godot/README.md#3-1-품질-단계)에 있다.

| 항목 | low | medium | high |
|---|---|---|---|
| 렌더러 | Compatibility | Mobile | Mobile |
| 루트 뷰포트 너비 | 540 | 720 | 원본(1200) |
| MSAA | 끔 | 2x | 2x |
| 그림자 | 끔 | 직교 1장, 1024 | Phase 0 모드, 2048 |
| S2 배경 | 단색 | 단색 | 절차적 하늘 |
| S1 glow | 끔 | 켬 | 켬 |

- low: 3-3의 Compatibility 540 조건. MSAA는 성능 차이가 없었지만(60.0 vs 60.0, p95 19.0 vs 18.2 ms) 여유를 남기려고 껐다.
- medium: Mobile 렌더러를 유지해 high와 바로 전환된다. 그림자는 직교 1장으로 남기고 하늘만 뺐다.
- high: Phase 0 그래픽 그대로다.
- MultiMesh·공 분할 수·3D 배율은 효과가 없거나 루트 뷰포트 너비보다 못해 단계에 넣지 않았다.

## 7. 남은 차이와 한계

- **low의 긴 프레임은 수집기 영향이다.** 2차 low는 장면마다 90초 × 3회에 33 ms 넘는 프레임이 정확히 24개(0.15%)였고, 10.5초 간격으로 생겼다. `collect.sh`가 10초마다 앱 프로세스의 `dumpsys meminfo`를 부를 때 앱이 잠깐 멈춘다. 메모리 조회가 실패했던 1차에는 같은 장면에서 0–2개였다. Phase 0 결과의 1% low도 같은 영향을 받았을 수 있다. 측정 기준을 고칠지(메모리 조회 간격·방식)는 사용자와 정할 일이라 바꾸지 않았다.
- **medium·high는 60 fps가 아니다.** medium 38–42 fps, high 11–28 fps다. 출시 기준은 "하한 기기 저품질 60 fps"이므로 판정에는 영향이 없다. 중급폰 고품질 60 fps는 이 Task에서 재지 않았다.
- **low의 그래픽 손실**: 그림자 없음, 단색 배경, 540 기준으로 그린 뒤 확대해 UI·가장자리가 흐리다. 강철(metallic 1.0)은 반사할 하늘이 없어 어둡게 보인다. UI 배치 기준도 540이 돼 버튼이 화면 대비 1.33배 커진다. 앱 셸(Task 2)에서 2D UI를 원본 해상도로 따로 그릴지 정해야 한다.
- **렌더러 이원화 비용**: low만 Compatibility라 단계 전환 시 재시작이 필요하고, 셰이더·조명 차이를 두 렌더러에서 확인해야 한다. Web도 Compatibility이므로 low와 Web 화면은 가깝다.
- **CPU 여유**: S2 물리 스텝이 한 번에 3.5–9 ms(`physics_ms`)다. low에서는 4.7 ms로 예산 안이지만, 물체 수가 늘면 CPU가 다음 병목이 될 수 있다.
- **측정 조건**: USB 연결(충전 중), 밝기 128/255. GPU 클럭은 AP 온도에 따라 바뀌어 짧은 측정은 시작 온도에 민감하다. GPU 시간은 Vulkan 타임스탬프 기준이고 Compatibility에서는 잴 수 없다.
- 콜드 스타트는 재지 않았다. low는 첫 전환 때 재시작이 한 번 더 든다.
