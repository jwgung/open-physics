# ADR 0001: 3D 앱 스택 — Godot 4 + Jolt

> **Status:** 채택됨
> **Date:** 2026-10-21
> **Context docs:** [측정 기준](../3d-phase0/benchmark-spec.md) · [후보 조사](../research/3d-stack-candidates.md) · [실측 결과](../../spikes/bench/results/README.md) · [WebGPU 누수 조사](../../spikes/bench/leak-repro/README.md)

## 맥락

Open Physics를 3D 모바일 앱으로 출시한다.

- 대상은 iOS와 Android다. 무료·무광고이며 아동도 사용한다.
- 웹 버전도 같은 콘텐츠로 유지하되, 그래픽은 앱보다 한 단계 낮아도 된다.
- 첫 출시는 역학 3D다.
- 하나의 범용 3D 물리 엔진 위에서 안내형 실험의 핵심 운동과 표시 수치를 교과서 공식값으로 보정한다.
- 개발은 AI 에이전트가 CLI로 주도한다.

후보는 두 가지였다. 같은 기준 장면 S1~S3로 스파이크를 만들어 비교했다.

- A: Three.js r186(WebGPURenderer, WebGL2 fallback) + Rapier 0.21 + Capacitor 8
- B: Godot 4.7.2 + Jolt

## 측정 결과 요약

하한 기기 SM-P200(Mali-G71, Vulkan 1.1, Android 11, WebView 155)에서 측정했다. 두 스파이크 모두 최적화하지 않은 상태다. 수치는 셀프 리뷰에서 측정 방식 차이를 바로잡은 뒤의 2차 측정값이다([결과](../../spikes/bench/results/README.md)).

측정 조건에는 다음 한계가 있다.

- 측정 기준 2절과 달리 USB로 연결해 충전 중이었고, 밝기는 128/255였다.
- 콜드 스타트는 첫 프레임이 아니라 `am start -W` TotalTime이다.
- 10분 동안 thermal status는 0이었다. 따라서 "스로틀링 없음"은 이 기기의 낮은 GPU 부하에서 나온 결과로 읽는다.
- 스파이크마다 안티에일리어싱, 렌더 해상도, S2 그림자 설정이 다르다. 그래서 장면별 FPS 차이를 엔진 우열로 읽지 않는다([결과 주의 사항](../../spikes/bench/results/README.md#비교-시-주의-렌더-설정이-같지-않다)).

| 항목 | Godot + Jolt | Three.js WebGPU | Three.js classic WebGL |
|---|---|---|---|
| S1 궤도 FPS | **26.0** | 20.0 | 5.8 |
| S2 빈 실험실 FPS | 11.6 | **25.8** | 7.9 |
| S3 빗면 마찰 FPS | **24.3** | 22.1 | 19.7 |
| S2 10분 PSS 추이 | 238 → 225 MB (평탄) | 189 → 1,137 MB (약 90 MB/분 증가) | 110 → 117 MB (평탄) |
| APK | 93.7 MB | **5.1 MB** | 5.2 MB |
| 웹 빌드(gzip) | 36.8 MB | **1.9 MB** | 1.9 MB |
| S3 공식 일치 | 통과(오차 ≤ 0.02%) | 통과(오차 ≤ 0.44%) | 같은 코드 |
| 공식 코어 | GDScript로 이식하고 parity 테스트 | 기존 TS 코어를 직접 import | 같음 |

## 판정 경과

1. **커트라인**: 두 후보 모두 하한 기기의 최고 품질 30fps에 미달했다. Plan의 재합의 경계에 해당했지만, 사용자는 재합의 없이 현재 결과로 진행하기로 했다(2026-10-21). 저품질 60fps 기준은 Phase 1 출시 기준으로 넘긴다.
2. **체감 평가**: 사용자가 생략했다(2026-10-21).
3. **첫 판정**: 장면별 우열이 엇갈려 동률 규칙(개발 효율·웹 품질)으로 A를 조건부 채택했다. 조건은 웹 S2 메모리 증가의 원인을 찾아 없애고, 해결하지 못하면 재검토하는 것이었다.
4. **누수 원인 조사**([조사](../../spikes/bench/leak-repro/README.md)):
   - 원인은 앱 코드가 아니었다. 이 기기의 Android WebView 155는 WebGPU(compatibility 모드)에서 프레임마다 네이티브 힙을 누수한다.
   - three.js와 Rapier 없이 화면만 지우는 최소 WebGPU 페이지에서도 120~170 MB/분씩 늘었다.
   - 앱 코드로는 고칠 수 없으므로 재검토 조건에 해당한다.
5. **WebGL 대안 확인**:
   - 누수를 피하려고 같은 장면을 기존 `WebGLRenderer`로 측정했다. 사전 판정 기준은 "S2가 Godot 이상이고, 10분 메모리가 평탄할 것"이었다.
   - 메모리는 평탄했지만 S2가 측정 평균 7.9 fps로 Godot의 11.6 fps보다 느렸다. 기준을 넘지 못했다.
   - 다만 classic S2는 vsync 경계에서 약 8 fps와 약 14.7 fps 상태를 오갔다. 10분 평균은 10.35 fps였고, 시간 비율은 8 fps 57%, 14.7 fps 33%였다. 그래서 이 판정은 경계선이다([결과](../../spikes/bench/results/README.md#webgpu-누수와-webgl-대안)).
   - S1은 5.8 fps였다. 이 측정에는 MSAA가 두 번 걸린 불리한 설정이 섞여 있다.

이 기기에서 웹 스택은 두 경로 모두 쓸 수 없다. WebGPU는 빠르지만 메모리가 새고, WebGL은 메모리는 안정적이지만 느리다. 성능과 안정성이 기기의 WebView·GPU 드라이버 품질에 달려 있고, 우리가 통제할 수 없다. 반면 Godot은 네이티브 Vulkan에서 메모리가 평탄했다. 품질을 최우선으로 하는 제품 목표에서는 이 통제 불가능한 위험이 개발 효율보다 크다.

**결정: B(Godot 4 + Jolt)를 채택한다.**

## 감수하는 비용

- **공식 코어 이중 유지**: TS 공식 코어(`src/physics/laws/`)는 정답 기준(oracle)으로 남는다. 앱에서 쓰는 공식은 GDScript로 이식한다. 공식을 바꿀 때마다 벡터 생성기, JSON, GDScript 포트, Godot 테스트 네 곳을 함께 고친다. `npm run test:spikes`와 Godot 헤드리스 테스트가 일치를 지킨다.
- **웹 품질**: 웹은 Compatibility(WebGL2) 렌더러로 내보낸다. 크기는 36.8 MB(gzip)이고 그래픽은 앱보다 낮다. 이는 Plan의 "웹은 한 단계 낮아도 됨"과 맞는다.
- **CI**: Node와 Godot 바이너리(약 150 MB)가 둘 다 필요하다.
- **앱 크기**: 93.7 MB(arm64, 2048² 텍스처)다. 텍스처 압축과 크기 조정으로 줄인다.

## 아동 정책

무료·무광고·아동 포함 결정에 따라 계정·서버·광고·제3자 추적을 두지 않는다. 후보 조사 5절에 따르면 Apple Kids Category와 Google Play Families 요건은 광고·분석 SDK를 넣지 않는 한 두 스택 모두 충족한다. 외부 링크는 보호자 확인(parental gate) 뒤에 두고, 개인정보처리방침(수집 없음)을 둔다. Godot 스파이크 APK는 권한을 요청하지 않는다. 제품에서도 이 상태를 유지한다.

## 조건과 후속 확인

- **S2 성능(최우선)**:
  - Godot S2는 11.6 fps로 세 장면 중 가장 느리다. Phase 1 첫 Task에서 병목을 찾는다. 후보는 그림자 `PARALLEL_2_SPLITS`, 물체 50개의 드로우콜, Jolt 스텝이다.
  - 저·중·고 품질 단계도 같은 Task에서 만든다. 출시 기준은 하한 기기 저품질 60fps, 중급폰 고품질 60fps다.
- **iOS 확인**: Godot은 iOS에서도 네이티브(Metal)로 돌아가므로 Plan에 따라 Phase 1 출시 준비에서 확인한다. 중급 iPhone, macOS 빌드 환경, Apple 개발자 계정이 필요하다.
- **엔진 동작 의존**: 공식 보정은 실험으로 확인한 두 가지 Godot·Jolt 동작에 기댄다. 하나는 콜백 순서(`_physics_process`에서 힘을 넣음)이고, 다른 하나는 정지 출발 첫 스텝의 반 힘 보정이다. 둘 다 문서화된 계약이 아니다. 그래서 Godot·Jolt를 올릴 때마다 S3 테스트를 다시 돌린다.
- **공식 보정 일반화**: S3 방식(엔진 마찰 0 + 공식 마찰력 주입)은 알려진 단일 접촉에서만 검증됐다. 빈 실험실의 일반 접촉에 적용하려면 Jolt 접촉 콜백 범위를 조사해 따로 설계한다.
- **터치 조작**: 두 손가락 회전·확대와 드래그 스냅은 실기기에서 아직 확인하지 않았다.

## 결과

- 3D 앱은 같은 저장소 `apps/` 아래 Godot 프로젝트로 시작한다. `spikes/godot/`의 구조, 측정 도구, parity 테스트를 출발점으로 쓴다.
- TS 공식 코어 `src/physics/laws/`는 정답 기준으로 계속 쓰고, 웹 2D 제품도 그대로 이 코어를 쓴다.
- 웹 2D는 유지보수만 한다(기능 추가 동결).
- `spikes/web-threejs/`와 누수 재현 도구는 비교 근거로 남기고 더 개발하지 않는다.

## Phase 1 Task 초안 (발행 전 사용자 승인 필요)

1. S2 성능 병목 조사와 품질 단계(저·중·고)
2. 3D 앱 셸: Godot 프로젝트 구조, 카메라 모드, 터치 제스처, 조작 평면·스냅, 2D 패널 레이아웃
3. 공식 보정 계층 일반화와 TS↔GDScript parity 파이프라인(CI 포함)
4. 역학 안내형 10개 3D 이식(실험별로 나눠 발행)
5. 역학 빈 실험실 3D(고정 블록·줄·용수철·지렛대·도르래·힘·중력원·물)
6. 출시 준비: 서명, 스토어 자료, 개인정보처리방침(수집 없음), Kids/Families 정책, 모바일 CI, iOS 실기기 확인
